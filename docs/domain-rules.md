# Domain rules (from the Fonepoints OMS PRD)

## Identity

- `salesOrderId` — Providhy Sales Order (the underlying record).
- `omsOrderId` — generated by OMS *after* the Sales Order is created; used by the rider portal.
- `fonepointsRef` — Fonepoints Transaction/Reference ID; the idempotency key.
- A repeat `fonepointsRef` returns the existing `omsOrderId` and never creates a second order.

## Order fields received from Fonepoints

Reference ID, merchant, customer, items + quantity, order value, value type
(`points` | `points_money`), source = Fonepoints, redemption status = Redeemed.
Fonepoints does NOT send selling price in points, OMS Order ID, or voucher number.

- **Item:** a redeemed Fonepoints deal (photo, "<Partner>-<offer>" title, market price), usually
  one unit. **Value:** points (`orderValue`) plus optional cash in Rs (`cashAmount`), shown as
  "Rs 1,923 + 174 pts". See `docs/fonepoints-customer-side.md` → Deal listing.

- The customer provides all of this, and the merchant only reads it. There are two separate sets:
  - **Customer:** from the Fonepoints user profile, via login. Name, phone and location
    (`customerName`, `customerPhone`, `customerLocation`), plus photo and email.
  - **Delivery details:** typed on the redeem form when ordering. Name, phone, location, delivery
    date, note and remarks (`delivery.name`, `delivery.phone`, `delivery.address`,
    `deliveryDate`, `delivery.note`, `delivery.remarks`). Name and phone can differ from the
    profile.

## Statuses

`preparing → ready_for_delivery → delivering → delivered`, exception `failed`.

| From | To | Who | Condition |
|---|---|---|---|
| (new) | `preparing` | system | on successful creation |
| `preparing` | `ready_for_delivery` | merchant | — |
| `ready_for_delivery` | `delivering` | merchant | rider name, phone, vehicle number all set |
| `delivering` | `delivered` | system only | successful Fonepoints redemption |
| any except `delivered` | `failed` | system / CS | operational or system failure |
| permitted set | permitted set | CS with override permission | audited |

`failed` never rolls back the underlying Sales Order.

**Open question:** the PRD says CS may override "permitted fulfillment statuses" without
listing them. Until confirmed, the prototype does NOT allow CS to set `delivered`. The
permitted set lives in one constant, `CS_OVERRIDE_TRANSITIONS`, in `src/lib/domain`.

## Rider validation

Rider enters OMS Order ID + voucher number (or scans QR). OMS sends both to Fonepoints.

| Fonepoints result | OMS behavior | Message shown |
|---|---|---|
| success | mark `delivered`, sync to Fonepoints, log | success confirmation |
| mismatch | count attempt, log | "The two fields do not match" |
| already redeemed | log | "Voucher code already redeemed" |
| redemption failed | stay undelivered, count attempt, log failure | generic failure + retry |

- Never reveal whether an OMS Order ID exists when the pair doesn't match.
- Max 5 attempts per OMS Order ID. Always show remaining attempts; block at 0.
- Attempts are counted server-side (mock API), never trusted from the client.
- An unknown Order ID is counted and blocked like a real one and gets the identical response, so
  the counter itself can't reveal whether an order exists.
- Only an order that is `delivering` (or already redeemed and pending reconciliation) can be
  redeemed. Any other order answers like a wrong pair.
- Rules and exact copy: `consumesAttempt`, `isValidationBlocked`, `VALIDATION_MESSAGES` in
  `src/lib/domain/validation.ts`.

## CS override audit

Every override records: actor, previous status, new status, timestamp, CS override flag.
Only users with override permission see or can call the override.

## Integration reliability

- Status sync to Fonepoints fails → keep OMS status, record failure, retry, record success.
- Redemption succeeded but Sales Order update failed → keep the result, reconcile to
  `delivered`, never send a second redemption request.

## Activity log events

Order created, OMS Order ID generated, status changed, rider assigned, validation attempt
+ result, redemption, delivered, integration failure/retry, reconciliation, CS override.

## Access

Merchants reach OMS from the Fonepoints merchant portal (SSO, no OMS login) and only see
their own orders. Prototype replaces SSO with a dev role switcher.

Permissions (`src/lib/domain/permissions.ts`; role → permission map in `src/config/constants.ts`):

| Permission | Grants | Held by |
|---|---|---|
| `orders:own` | read and fulfill the caller's own merchant orders | Merchant A, Merchant B |
| `orders:all` | read orders across all merchants | CS agent, CS agent (no override) |
| `orders:override` | audited CS status override | CS agent |
| `sync:view` | failed status syncs and pending reconciliation | CS agent, CS agent (no override) |
| `deliver:validate` | voucher validation on delivery | Rider |

The rider portal (`/deliver`) has **no login**: the OMS Order ID + voucher pair is the
credential, and the attempt limit is the brute-force guard. The portal never reads or sets the
mock role, so it runs in a tab beside the merchant dashboard (opened from the OMS sidebar's
"Delivery portal"). `deliver:validate` stays in the role map but the UI doesn't check it.

Every route in `src/config/nav.ts` declares the permission it needs. The UI hides nav
items and shows a "switch role" state for routes the role can't open. The mock API must
enforce the same permissions server-side.

## Out of scope

Returns / reverse logistics, marketplace integrations, a separate OMS order engine.
